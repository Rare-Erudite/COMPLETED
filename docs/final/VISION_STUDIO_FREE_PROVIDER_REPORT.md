# Vision Studio — Free AI Image Provider Report

**Date:** 2026-11-27
**Starting commit:** `df26d52`
**Environment:** Debian sandbox, Node 20.20.2, no `DATABASE_URL`, no `GEMINI_API_KEY`

---

## 1. The problem

The previous report established that Gemini's image endpoint returned **HTTP 429 with a
free-tier image quota of `limit: 0`** — i.e. image generation was not merely rate-limited,
it was unavailable on that key at all. Vision Studio could therefore only produce
procedural vector artwork, which is **not** AI image generation.

## 2. Providers investigated

| Provider | Free image gen? | Payment method required? | Verdict |
|---|---|---|---|
| **Pollinations.ai** | **Yes** | **No** | **SELECTED** |
| Google Gemini image (`gemini-3-pro-image-preview`) | No — `429`, quota `limit: 0` | Yes, to raise quota | Rejected |
| Hugging Face Inference API (FLUX.1-schnell) | No — endpoint unreachable (`000`) without a token | Yes (token/plan) | Rejected |
| Local diffusion (Stable Diffusion / SDXL) | Technically possible | No | Rejected — sandbox has 773 MB RAM; SD needs ≥4 GB VRAM/RAM. Not practical on the owner's stated hardware. |

### Why Pollinations

- **No API key, no account, no payment method, no trial.** A plain `GET` returns an image.
- **No billing risk whatsoever** — there is no account to upgrade and no card on file.
- Real model output (FLUX / "sana" family), not a placeholder.
- Free tier is **paced, not metered**: 1 image per 45 s per IP. Exceeding it returns
  `HTTP 402 {"code":"FREE_LIMIT"}` — a throttle, not a paywall.

## 3. Implementation

**New file:** `src/server/providers/FreeImageProvider.ts`

- `generateFreeImage()` — single attempt. Throws a typed `FreeImageError`
  (`rate_limited` / `timeout` / `provider_error` / `invalid_response`) and **never**
  returns a placeholder, so a caller can never mistake a failure for a real image.
- `generateFreeImageWithRetry()` — retries the 45 s throttle with backoff (3 attempts,
  20 s/40 s). This is what stops a second consecutive request from silently degrading
  to procedural output.
- `probeFreeImageProvider()` — live reachability probe for the status endpoint.
- `dimensionsForAspect()` — maps RARE's aspect vocabulary to real pixel dimensions.
- MIME is **sniffed from magic bytes**, not trusted from the header, and an HTML error
  page returned with HTTP 200 is rejected as `invalid_response`.

**Wiring in `server.ts`:**

- `/api/images/generate` — free provider first → Gemini second → procedural last.
- `/api/images/edit` — same order.
- `/api/images/status` — now probes the provider live and reports `activeProvider`,
  `freeProvider`, `geminiImage` and `proceduralFallback` honestly.
- `ImageRecord` gained `aiGenerated`, `provider`, `latencyMs`, and `source` now includes
  `'free_provider'`.

**New endpoints:**

- `POST /api/images/export` — writes the image into Documents.
- `GET /api/images/:id/download` — streams the real image bytes with correct
  `Content-Type` and `Content-Disposition`.

### Export to Documents — PARTIAL

`POST /api/images/export` returns `201` and writes a record, **but** Documents storage
is text-only (`DocumentsService.save` stores extracted text, not binary blobs). The
exported artefact is therefore a **description of the image**, not the image file.

This is a real architectural limitation, not a bug I introduced. The honest equivalent
is `GET /api/images/:id/download`, which delivers the actual bytes. Making Documents
hold binary images would require a blob store, which is out of scope for this phase.

## 6. Remaining limitations

1. **45 s throttle.** One image per 45 s per IP. Retry-with-backoff absorbs this for
   normal use; a burst of many images will queue.
2. **Editing is regeneration, not inpainting.** No mask support.
3. **Documents cannot store binary images.** Use the download endpoint.
4. **Gemini image path is dead on the current key** (`limit: 0`). The code path remains
   for when a key with image quota exists.
